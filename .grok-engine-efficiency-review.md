# Cut engine efficiency review

Full-tree review of the current Rust media stack (`cut-engine`, `cut-core`, `cut-playback`, `cut-runtime`, plus `cut-app` playback/preview call sites). Not a git-diff review.

## Summary

The engine is a well-budgeted **ffmpeg-CLI compositor**, not an in-process media runtime. Compile, resource caps, derivative caching, and ONNX tracking are already thoughtful. Almost every hot path still **spawns ffmpeg** (or cut-engine, which then spawns ffmpeg), copies frames into new `Vec`/`Arc` buffers, and rebuilds filtergraphs and decoder processes on every seek or clip change.

What is already good: process-wide ffmpeg binary/hwaccel/encoder caches, laptop CPU budgets, mimalloc + thin LTO, bounded playback queues, tracking downscale-before-RGB, and in-process ONNX (no Python). What is leaving the most performance on the table: CLI decode for preview, output-side range seeks that still run the full graph, v2 compositing in full-resolution RGBA, and a per-sample mutex in the audio callback.

Qualitative ceiling: **preview/playback is process-spawn bound, ~25–40% of a native persistent libav decoder** with GOP cache and GPU textures. **Offline export is ~50–65% of a well-tuned ffmpeg graph** (input `-ss`, yuv overlay, no `geq`). **YOLO is ~40–60% of a GPU EP + ffmpeg-padded 640² tensor**. Overall the engine is a solid v1 NLE backend, not a realtime compositor.

## Architecture snapshot

```
cut-app  --JSON-lines Unix IPC-->  cutd (cut-runtime)
                                      |  spawn cut-engine CLI
                                      v
cut-core compile_v1/v2  -->  ffmpeg argv + filter_complex
                                      |
                                      +--> render / proxy / probe / filmstrip / waveform
                                      +--> whisper.cpp sidecar (transcription)

cut-app ViewerPlaybackAdapter  -->  cut-playback worker thread
                                      |  spawn ffmpeg rawvideo RGBA pipe (per clip/seek)
                                      +  spawn ffmpeg f32le audio pipe (per clip/seek)
                                      v
                                   egui ColorImage -> wgpu texture

cut-engine track  -->  ffmpeg rgb24 pipe (fps+scale) --> letterbox NCHW
                   -->  ONNX Runtime (CPU, feature-gated) --> NMS --> ByteTrack
```

There is **no ffmpeg-next / libav**. `cut-engine` and `cut-playback` talk to ffmpeg exclusively via `std::process::Command`. Playback does **not** go through cutd (good). Export/preview-fallback does: app → cutd JSON → **new cut-engine process** → **new ffmpeg process**.

## What is already efficient

- **Release profile is serious.** Workspace `release` uses `opt-level=3`, thin LTO, `codegen-units=1`, `panic=abort`, strip; `maxperf` is fat LTO. Engine process uses mimalloc (`crates/cut-engine/src/lib.rs:3-4`).
- **ffmpeg sidecar metadata is cached once per process.** Binary path, hwaccel args, encoder listing, and decode thread prefix live in `OnceLock` (`crates/cut-engine/src/ffmpeg.rs:44-132`, `238-242`). Comments there correctly note that re-running `ffmpeg -version`/`-encoders` used to dominate engine-side time.
- **Laptop resource budget.** Thread caps, extract parallelism, tracking fps, x264 preset/CRF, hardware-encode policy (`crates/cut-engine/src/resources.rs:70-174`). 4-core machines get 2 ffmpeg threads / `veryfast` / CRF 23; 16-core gets 8 threads / `medium` / CRF 20.
- **Decode hwaccel is on for engine jobs** (VideoToolbox / D3D11VA) (`crates/cut-engine/src/ffmpeg.rs:86-119`). Hardware encode is Auto by default (`resources.rs:163-174`).
- **Draft export is cheap:** scale 360p + fps 15 + `ultrafast` CRF 35 (`crates/cut-engine/src/render.rs:63-74`).
- **Compile is a pure string builder** in dependency-light `cut-core`. Regexes are `LazyLock`. This path is not the bottleneck versus decode/encode.
- **Derivative cache** for exact frames, filmstrips, waveforms, transcripts (`crates/cut-engine/src/derivatives.rs`). Probe results cached by size+mtime (`crates/cut-engine/src/probe.rs:241-296`).
- **Tracking pipeline already does the important ffmpeg-side reductions:** sample at 8 fps (5 on 2-core), scale long edge into `imgsz` before RGB, 1 MiB pipe buffer, reused letterbox/`YoloRawOutput` scratch (`crates/cut-engine/src/vision/yolo.rs:199-225`, `248-254`, `428-436`, `787`).
- **ONNX is in-process and thread-capped:** GraphOpt Level3, intra-threads from budget, inter-threads=1 (`crates/cut-engine/src/vision/onnx.rs:17-28`). No Python Ultralytics at runtime.
- **Playback isolation is well designed:** worker thread, bounded decode queue (4) and event queue (64), drop frames when UI is slow, retain control events (`crates/cut-playback/src/lib.rs:23-29`, `108-110`, `670-690`). Frames are `Arc<[u8]>` so the UI can hold them without a second pixel clone at the worker boundary.
- **Preview policy is cheap:** `analyze_project` is a checker pass, not a render (`crates/cut-core/src/preview.rs:107-165`).
- **IPC does not carry pixels.** cutd is JSON command/state; playback lives in-process in the app. Request size capped at 1 MiB (`crates/cut-runtime/src/lib.rs:51`).
- **Frame extraction is parallel and capped** via `thread::scope` + `CUT_EXTRACT_JOBS` (`crates/cut-engine/src/probe.rs:384-410`). Thumbnail path uses input-side `-ss` (`probe.rs:350-353`).

## Issues

### Issue 1 -- Severity: bug
- File: `crates/cut-engine/src/render.rs:417-428`
- Description: `render_v2_range_*` pops the output path and appends **output-side** `-ss` / `-t` after the full v2 filtergraph. The compiler still builds a `color=...:d={full timeline duration}` base and overlay graph for the **entire project** (`crates/cut-core/src/compile.rs:1906-1913`, `1235-1283`). ffmpeg must run that graph from t=0 until the range, then discard. Preview fallback in `cut-app` uses this path (`crates/cut-app/src/lib.rs:588-632` with `draft: true` and a `RenderRange`).
- Suggestion: compile a range-aware graph (shorten the color source, shift clip `enable`/`setpts`, or emit per-clip input `-ss`). At minimum put `-ss`/`-t` on inputs that overlap the range, not after `-filter_complex`.
- Status: open
- Impact: latency / CPU (preview of 3s in a 10 min timeline still decodes minutes of media)

### Issue 2 -- Severity: suggestion
- File: `crates/cut-playback/src/decoder.rs:17-86`, `107-125`; call site `crates/cut-app/src/viewer.rs:352`
- Description: Every clip change and every seek **kills ffmpeg and respawns** (`crates/cut-playback/src/lib.rs:484-523`, `580-591`). Each process decodes to **full canvas RGBA** over a pipe (`decoder.rs:66-70`). The app never sets `frame_width`/`frame_height`, so a 1920×1080 project is ~8.3 MB/frame uncompressed; 4K is ~33 MB/frame. `next_frame` allocates a fresh `Vec` then `Arc::from(boxed)` every frame. No GOP cache, no persistent codec context, no default hwaccel (only if `CUT_HWACCEL` is set — unlike the engine).
- Suggestion: keep one ffmpeg (or libav) context per source; input `-ss` + `read_frame` reuse; decode NV12/YUV to a GPU texture or at least to a reused RGBA buffer; default viewer size to the widget (e.g. 960×540) via `PlaybackConfig::with_frame_size`.
- Status: open
- Impact: latency (seek/scrub), throughput (playback), memory (full-res RGBA queue)

### Issue 3 -- Severity: bug
- File: `crates/cut-playback/src/audio.rs:641-646`, `812-828`
- Description: The cpal callback calls `buffer.pop()` **once per sample**. `pop` takes a `Mutex<VecDeque<f32>>` for every sample. At 48 kHz stereo that is ~96k lock/unlock pairs per second on the realtime thread. `push` also locks and `extend`s. Combined with a 4 ms decode tick (`AUDIO_TICK`, line 16) this is both a glitch source and wasted CPU.
- Suggestion: lock once per callback, `pop` a contiguous slice (or use a lock-free ring buffer / `rtrb`). Apply volume/mute on the copy. Keep the mutex off the per-sample path.
- Status: open
- Impact: latency (audio glitches), CPU

### Issue 4 -- Severity: suggestion
- File: `crates/cut-core/src/compile.rs:1235-1283`, `1936-1938`, `1891-1903`
- Description: v2 clips are trimmed **inside the filtergraph** (`trim=start:end`) from a single `-i` per source with **no input `-ss`**. ffmpeg decodes from the start of each file (or from the previous keyframe without a seek hint) for every clip. After trim, every clip is forced to **`format=rgba`**, color/opacity (`geq` is a software per-pixel filter at lines 1264-1269), then `overlay` onto an RGBA canvas. There is **no scale-to-canvas** unless the user set transform scale. A 4K source on a 1080p project is overlaid at 4K. Final `format=yuv420p` is after all overlays (`1953-1955`). v1 is better: it scales/pads/format=yuv420p per clip (`crates/cut-core/src/compile_v1.rs:220-232`).
- Suggestion: emit `-ss`/`-t` (or `-read_intervals`) per used source segment; composite in yuv420p/nv12 at canvas size; replace `geq` alpha with `colorchannelmixer`/`geq` only when keyframed; `overlay=format=yuv420`.
- Status: open
- Impact: throughput / CPU / memory (export and draft preview)

### Issue 5 -- Severity: suggestion
- File: `crates/cut-engine/src/ffmpeg.rs:1-5`, `134-167`; `crates/cut-engine/Cargo.toml` (no ffmpeg-next/libav)
- Description: The entire engine is process-spawn. `run()` captures full stdout+stderr into new `String`s via `from_utf8_lossy` every call. Probe, silence, scenes, frames, proxy, render, tracking decode, and waveform all pay `fork/exec` + ffmpeg startup (filters, decoder init). cutd then wraps that in **another** process: `Command::new(engine_binary)` for probe (`crates/cut-runtime/src/lib.rs:3820-3824`) and render (`5356-5388`).
- Suggestion: keep CLI ffmpeg for export (it is the right tool). For probe/info, waveform, single-frame grabs, and playback, link libavformat/libavcodec (ffmpeg-next or a thin FFI) and reuse contexts. In-process `cut-engine` as a library from cutd would remove the extra process on probe/render.
- Status: open
- Impact: latency (probe/import/scrub), CPU (startup)

### Issue 6 -- Severity: suggestion
- File: `crates/cut-engine/src/probe.rs:444-467` vs `338-361`
- Description: Thumbnail `extract_one_frame` seeks **before** `-i` (fast). Exact frames / filmstrip seek **after** `-i`, so each timestamp decodes from the beginning of the file. Up to 128 timestamps (`MAX_FRAME_TIMES`), each a full ffmpeg process, even with `extract_job_count` parallelism. PNGs, not JPEG/WebP.
- Suggestion: input `-ss` to the previous keyframe, then accurate decode for the last GOP; or one ffmpeg with a select/filter and image2 muxer. Prefer jpeg/webp for filmstrips.
- Status: open
- Impact: latency / CPU (bin + filmstrip on long GOP sources)

### Issue 7 -- Severity: suggestion
- File: `crates/cut-app/src/viewer.rs:526-587`; `crates/cut-playback/src/lib.rs:626-641`
- Description: UI thread copies the latest frame again via `ColorImage::from_rgba_unmultiplied` (another width×height×4 alloc+copy) then `texture.set`. Captions are cloned onto every `PlaybackFrame` (`captions_at` clones matching cues, `timeline.rs:252-257`). `clip_id: String` is cloned per frame (`lib.rs:636`).
- Suggestion: upload with `ColorImage::from_rgba_unmultiplied` only if needed; consider `egui::ColorImage` from a reused buffer or a wgpu texture filled on the worker. Attach captions by reference / small IDs. Cap presented size to the viewer rect.
- Status: open
- Impact: memory / CPU (UI thread hitch on 1080p/4K)

### Issue 8 -- Severity: suggestion
- File: `crates/cut-engine/src/vision/onnx.rs:19-26`, `59-67`; `crates/cut-engine/src/vision/yolo.rs:199-212`, `518-567`
- Description: ONNX uses the default CPU EP only (`ort` features: `std`, `ndarray`, `download-binaries` — no CUDA/CoreML/DirectML). ffmpeg already scales to `new_w×new_h` (e.g. 640×360), then CPU letterbox nearest-neighbor resamples into 640×640 NCHW. Inference copies the full output tensor (`onnx.rs:97-98`). `track_video_frames` retains **every** `DetectionFrame` in a `Vec` (`yolo.rs:361-412`). `device` in vision config is accepted and ignored (`config.rs:300`).
- Suggestion: pad to `imgsz` in the ffmpeg vf (`scale+pad`) so letterbox hits the `width==imgsz` u8→f32 fast path; enable CoreML/CUDA EPs; decode YOLO output in-place without `extend_from_slice` when layout is already contiguous; stream JSONL/normalize per frame instead of buffering the whole video.
- Status: open
- Impact: throughput / CPU (tracking)

### Issue 9 -- Severity: suggestion
- File: `crates/cut-engine/src/vision/nms.rs:36-66`; `crates/cut-engine/src/vision/bytetrack.rs:147-211`; `crates/cut-engine/src/vision/mod.rs:225-227`
- Description: NMS inner loop walks **all** boxes for every keeper, including already-suppressed ones (O(n²) with a large constant). ByteTrack assignment is greedy sort, not Hungarian (fine at NLE object counts). `round_coordinate` does `format!("{:.12}", value).parse()` per bbox component during normalize/plan. Planning clones detections, keyframes, and class-split vectors (`planning.rs:236-237`, `379-416`, `489-512`).
- Suggestion: iterate remaining candidates only; round with ` (value * 1e12).round() / 1e12 `; plan from references. NMS is not the bottleneck vs ONNX unless conf is very low.
- Status: open
- Impact: CPU (tracking postprocess; secondary)

### Issue 10 -- Severity: suggestion
- File: `crates/cut-engine/src/probe.rs:697-719`
- Description: Waveform decodes the **entire** audio stream to f32le in one ffmpeg process, then allocates `Vec<f64>` of every sample at 8 kHz (`WAVEFORM_SAMPLE_RATE = 8000`). One hour ≈ 28.8e6 samples × 8 bytes ≈ 230 MB, plus the original f32 stdout buffer. Bucketing is a second full pass. Optional `showwavespic` is a **second** full decode (`728-743`).
- Suggestion: bucket while reading f32 in chunks (no `Vec<f64>`); generate the image from buckets or a single ffmpeg graph (`aformat,showwavespic`); downsample in ffmpeg (`aresample=1000`) if only N buckets are needed.
- Status: open
- Impact: memory / CPU

### Issue 11 -- Severity: suggestion
- File: `crates/cut-runtime/src/lib.rs:1345-1634`, `2450-2461`
- Description: `RuntimeClient::request_once` opens a **new UnixStream per request**, serializes the full `RuntimeRequest` (often including project JSON), reads one line, disconnects. `durable_state()` clones the entire project, history, jobs, and proposal on many commits. Probe/render additionally spawn `cut-engine`. This is fine for edits; it is wasteful for high-frequency `GetState` / render progress (`cut-app` progress callback also does `update_render_job` over IPC, `lib.rs:644-650`).
- Suggestion: persistent connection + length-prefixed frames; progress over a side channel or in-process callback when app and engine share a process; avoid cloning `project` on progress-only job updates.
- Status: open
- Impact: latency (editor chatter), not pixel throughput

### Issue 12 -- Severity: suggestion
- File: `crates/cut-engine/src/encoder.rs:206-226`; `crates/cut-engine/src/proxy.rs:263-295`
- Description: Software encode gets CRF+preset. VideoToolbox gets `-q:v 65` only. NVENC/QSV/AMF get **codec name only** — no `-cq`/`-rc`/`-preset`/`-b:v`. Proxy hardware path uses the same helper. Quality and speed will be whatever ffmpeg defaults are (often slow or wrong bitrate).
- Suggestion: per-family args (nvenc `p4` + `-cq`; qsv `veryfast` + global_quality; amf quality). Keep software fallback as today.
- Status: open
- Impact: throughput / quality of proxy+export

### Issue 13 -- Severity: nit
- File: `crates/cut-playback/src/decoder.rs:54-58` vs `150-154`
- Description: Comments disagree with the code. Args put `-ss` **before** `-i` (fast/input seek). The filter comment still says “`-ss` is intentionally after `-i`”. Easy to “fix” the code in the wrong direction.
- Suggestion: document input `-ss` + `trim=duration` as the intended path; add an accurate-seek flag if editors need frame-exact scrub.
- Status: open
- Impact: none until someone “corrects” it

### Issue 14 -- Severity: nit
- File: `crates/cut-core/src/compile.rs:1973-1986`; `crates/cut-engine/src/render.rs:110-133`
- Description: Compiler builds `argv` **and** a joined `command` string. Render then clones argv, skips `[0]`, truncates the last two fps args, and re-appends fps/codec. Lots of `String` clones for a one-shot export — cheap vs ffmpeg, noisy.
- Suggestion: compile to a structured `RenderPlan { inputs, filter_complex, maps }` and format argv once in `render.rs`.
- Status: open
- Impact: negligible CPU; compile-graph complexity

### Issue 15 -- Severity: nit
- File: `crates/cut-engine/src/render.rs:24-25`, `310-349`
- Description: Render progress polls `try_wait` every 20 ms on a dedicated thread while a reader thread already streams stderr. Fine, but it is a sleep loop rather than blocking on the child.
- Suggestion: `wait()` on the child (or poll with a longer interval) and let the stderr thread be the progress source.
- Status: open
- Impact: negligible CPU

### Issue 16 -- Severity: suggestion
- File: workspace `Cargo.toml` / crate `Cargo.toml` files — **no** `criterion`, `divan`, `[[bench]]`, or engine timing harness
- Description: Tests cover parse/compile correctness and a few ffmpeg integration gates (`cut-playback/tests/ffmpeg_playback.rs`, `release_gate.rs`). There is no bench for compile, letterbox, NMS, playback frame time, or spawn overhead. `resources.rs` unit tests pin thread counts, not runtime.
- Suggestion: see Measurement gaps.
- Status: open
- Impact: no feedback loop for the issues above

## Highest-leverage next optimizations

1. **Persistent in-process decode for playback (and probe/frame grab).** Keep ffmpeg CLI for export. A long-lived decoder (ffmpeg-next or libav) with reused codec context, input `-ss`, optional hwaccel, and a viewer-sized RGB/NV12 target would move preview from ~30% to ~70%+ of ceiling. Pair with `PlaybackConfig::with_frame_size` in `cut-app` immediately even before libav — that is a one-file win for 4K.

2. **Range-aware compile + input seeks.** Fix `render_v2_range` (Issue 1) and add per-clip `-ss`/`-t` (Issue 4). This is the difference between draft preview being usable and “wait for the whole timeline.” Expected impact: 5–50× less work on sparse ranges; 2–10× on exports that only use a slice of a long source.

3. **Stop compositing full-res RGBA.** Scale each v2 clip to canvas in yuv420p (as v1 already does), overlay in yuv, reserve `format=rgba`/`geq` for actual transparency. Expected impact: large CPU and RAM drop on 1080p/4K export; often 2–4× filtergraph throughput.

4. **Audio callback: one lock per buffer.** Cheap, local, and it is currently a realtime bug. Expected impact: glitch-free playback; measurable UI/audio CPU drop.

5. **YOLO: pad in ffmpeg + GPU EP.** `fps=8,scale=W:H:force_original_aspect_ratio=decrease,pad=imgsz:imgsz` then the existing u8→f32 fast path; CoreML on macOS. Stream detections instead of `Vec<DetectionFrame>`. Expected impact: ~1.5–3× tracking fps on laptop GPU/ANE; lower RAM on long sources.

Honorable mention: exact-frame `-ss` before `-i` (with short accurate tail), waveform streaming buckets, NVENC quality flags, in-process `cut-engine` from cutd so probe is not a nested spawn.

One `CUT_PROFILE=1` stderr counter for spawn count per operation would make nested `cutd → cut-engine → ffmpeg` visible immediately.

## Parallelism notes

- **No rayon, no tokio** in the media crates. Work is ad-hoc `thread::spawn` / `thread::scope`.
- Overlap that exists: extract jobs, stderr readers, playback+audio workers, render cancel watchers.
- Underused: clip-parallel export (one ffmpeg graph is sequential by design — that is OK); ONNX batch>1 (not worth it at 8 fps sequential tracking); multi-source decode in playback (one clip at a time is correct for a single viewer).
- Oversubscription risk is already handled for decode+ONNX via `decode_threads` vs `ffmpeg_threads`. Playback ffmpeg is **uncapped** (`-threads` not passed in `decoder.rs` / `audio.rs`).
